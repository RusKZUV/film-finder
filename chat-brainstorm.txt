# Movie Discovery App — Project Plan

## 1. Project Overview

Build a web application that helps users discover movies based on their interests, ideas, moods, plot preferences, and natural-language queries.

Users describe what they want to watch. An AI interprets the request, finds relevant movies, ranks them, and explains why each movie is a good match.

The goal is to make movie discovery more intuitive than traditional searches based only on titles, genres, or keywords.

## 2. Project Scope — MVP

The first version will include:

- Natural-language movie search.
- AI-powered query interpretation and ranking.
- Integration with The Movie Database (TMDB) API.
- Movie filters.
- Search results displaying 20 movies.
- AI-generated explanations for recommendations.
- Personal watchlist stored locally in the browser.
- Responsive web interface.
- No user accounts or social features.

The MVP will focus on discovering movies rather than building a complete movie community or streaming platform.

## 3. Target Users

People who:
- Want to discover movies based on specific interests.
- Know what kind of experience they want but not which movie to watch.
- Prefer recommendations based on plots, themes, moods, and ideas.
- Want alternatives to conventional genre-based search.
- Appreciate explanations behind recommendations.

Example users' queries:

- "Movies about time loops with a surprising ending."
- "Something similar to Inception but less action-oriented."
- "Psychological thrillers with unreliable narrators."
- "Movies about artificial intelligence questioning humanity."
- "A relaxing, feel-good movie for tonight."
- "Movies where enemies gradually become friends."

## 4. Core User Journey

1. The user opens the application.
2. The user enters a natural-language query.
3. The user optionally adjusts filters.
4. The backend interprets the query using an LLM.
5. The backend retrieves candidate movies from TMDB.
6. The LLM ranks the candidates by relevance.
7. The application displays 20 ranked results.
8. Each result includes movie information and an AI-generated explanation.
9. The user can refine the query or adjust filters.
10. The user can save interesting movies to a personal watchlist.
11. The watchlist remains available in the same browser.

## 5. Search and Query Understanding

### Input

Provide a search field that accepts natural-language descriptions rather than requiring exact movie titles.

### AI interpretation

The LLM should identify relevant aspects of the request, such as:

- Themes and concepts.
- Plot elements.
- Mood and atmosphere.
- Character types and relationships.
- Narrative devices.
- Similarity to reference movies.
- Explicit preferences and exclusions.

The LLM should distinguish between strict requirements and softer preferences when possible.

For example:

Query:
"I want a science-fiction movie about time travel, with a mysterious atmosphere and little violence."

The interpreted preferences might be:

- Genre: science fiction.
- Theme: time travel.
- Mood: mysterious.
- Preference: low violence.
- Ranking priority: strong thematic and tonal match.

### Vague queries

The application should search immediately rather than requiring clarification.

For vague requests, the AI should make reasonable assumptions and return a varied set of relevant recommendations.

## 6. Movie Data Source

Use the TMDB API as the external movie data provider.

Retrieve available information such as:

- Movie title.
- Original title.
- Release date and year.
- Overview or plot summary.
- Poster and backdrop images.
- Genre information.
- Original language.
- Runtime, when available.
- Movie type.
- TMDB rating and vote count.
- Movie identifier.

Use TMDB discovery and search endpoints to retrieve candidate movies.

Apply available structured filters through the API where appropriate.

Important limitation:
TMDB's search and discovery endpoints do not directly understand every abstract concept, mood, or narrative preference. Candidate retrieval must therefore be broad enough to give the LLM useful alternatives to rank.

The MVP should use TMDB rather than importing and maintaining a separate movie catalog.

## 7. Candidate Retrieval and AI Ranking

Use a two-stage search process.

### Stage 1: Candidate retrieval

The backend should:

1. Receive the user's query and filters.
2. Extract structured preferences using the LLM.
3. Translate applicable preferences into TMDB search and discovery parameters.
4. Retrieve candidate movies from TMDB.
5. Combine and deduplicate results.
6. Gather sufficient movie metadata for ranking.

Retrieve more candidates than the 20 movies ultimately displayed, subject to practical API and latency limits.

### Stage 2: LLM ranking

The LLM evaluates candidate movies against the user's intent.

Ranking factors may include:

- Plot relevance.
- Theme relevance.
- Mood and atmosphere.
- Character and relationship relevance.
- Narrative similarities.
- Explicit requirements.
- Structured filter compatibility.

Use balanced relevance rather than strict matching or unrestricted diversity.

The AI should prioritize strong matches while retaining some variety.

The LLM must rank only movies present in the retrieved candidate set. It must not invent movie titles, plot details, ratings, or other factual information.

If metadata is insufficient to establish a match, the system should avoid unsupported claims.

## 8. Search Filters

Provide the following filters in the MVP:

- Genre.
- Release year range.
- Minimum rating.
- Language.
- Runtime.
- Movie type.

The interface should allow users to combine natural-language queries with structured filters.

Filters must remain authoritative constraints where applicable. The LLM should not promote a movie that violates an explicitly selected filter.

Only offer filters that TMDB can support reliably or that can be validated against returned metadata.

## 9. Search Results

Each search should return up to 20 ranked movies when sufficient candidates are available.

Display results in a responsive grid of movie cards.

Each card should contain:

- Poster.
- Movie title.
- Release year.
- Genre.
- Rating.
- Runtime, when available.
- Short plot overview.
- AI-generated explanation of relevance.

The explanation should connect actual movie details to the user's query rather than provide generic praise.

Example:

User query:
"Movies about time loops with a surprising ending."

Example explanation:
"This film explores repeated events and the consequences of trying to change the future. Its mystery-driven structure makes it a promising match for your interest in time loops."

The example is illustrative, not a factual recommendation for a particular movie.

The application should communicate when fewer than 20 suitable results are available rather than inventing additional matches.

## 10. Personal Watchlist

Allow users to save movies to a watchlist without creating an account.

Features:

- Add a movie to the watchlist.
- Remove a saved movie.
- View saved movies on a dedicated page or section.
- Prevent duplicate entries.
- Preserve the watchlist between browser sessions.

Use browser local storage for persistence.

Store the minimum information needed, preferably TMDB movie IDs and essential display metadata.

When rendering saved movies, handle deleted, unavailable, or changed metadata gracefully.

Limitations:
The watchlist will not synchronize between devices or browsers. Clearing browser data may remove saved movies.

## 11. User Interface

### Main page

Include:

- Application name and navigation.
- Prominent natural-language search field.
- Search button.
- Filter controls.
- Example queries for new users.
- Optional link to the watchlist.

### Results page or results section

Include:

- Original search query.
- Active filters.
- Number of returned results.
- Movie card grid.
- Ranking explanations.
- Loading indicators.
- Empty and error states.
- A way to edit the query and search again.

### Watchlist

Include:

- Saved movie cards.
- Remove controls.
- Empty-state message.
- Navigation back to search.

### Design principles

- Responsive layout for desktop and mobile browsers.
- Clear typography and readable movie cards.
- Poster-focused presentation.
- Accessible controls.
- Simple loading and error feedback.
- Avoid unnecessary animations and complex navigation in the MVP.

## 12. Technical Architecture

Use a frontend, backend, and external API architecture.

### Frontend

Responsibilities:

- Search input and filter controls.
- Results display.
- AI explanation display.
- Watchlist interface.
- Browser-local persistence.
- Loading, validation, and error states.

Suggested technologies:
- React.
- TypeScript.
- Next.js.
- Tailwind CSS.

### Backend

Responsibilities:

- Receive and validate search requests.
- Interpret queries with the LLM.
- Retrieve candidate movies from TMDB.
- Normalize and deduplicate metadata.
- Rank candidates using the LLM.
- Validate returned movie identifiers.
- Generate or validate explanations.
- Enforce request limits and timeouts.
- Handle errors and external API failures.

Suggested technology:
- Next.js server-side API routes using TypeScript.

### External services

1. TMDB API for movie metadata and candidate retrieval.
2. A hosted LLM API for query interpretation, ranking, and explanations.

The backend must call the LLM provider. Do not expose the LLM API key in browser code.

Keep API integrations isolated behind service modules so that the providers can be replaced later.

## 14. Suggested API Design

### POST /api/search

Purpose:
Search for movies using natural-language queries and optional filters.

Example request:

{
  "query": "Science-fiction movies about time travel",
  "filters": {
    "genres": [],
    "yearFrom": 2000,
    "yearTo": 2026,
    "minRating": 6.5,
    "language": "en",
    "minRuntime": null,
    "maxRuntime": 180,
    "movieType": "movie"
  }
}

Example response structure:

{
  "query": "Science-fiction movies about time travel",
  "results": [
    {
      "tmdbId": 123,
      "title": "Example Movie",
      "year": 2020,
      "posterPath": "/example.jpg",
      "rating": 7.2,
      "genres": ["Science Fiction"],
      "explanation": "Example explanation based on verified movie metadata."
    }
  ],
  "totalReturned": 1
}

The example data is illustrative only.

Actual responses should follow a documented TypeScript schema. Validate all incoming requests and model outputs before returning data to the frontend.

### Watchlist persistence

No watchlist backend endpoint is required for the MVP.

The browser manages local watchlist persistence.

## 16. AI Cost and Performance

The system should balance relevance, response time, and operating cost.

Recommended measures:

- Use a cost-effective hosted LLM with structured JSON output.
- Keep prompts concise.
- Retrieve a bounded number of candidates.
- Avoid sending unnecessary TMDB metadata to the model.
- Use a single ranking request where practical.
- Separate query interpretation from ranking only when necessary.
- Cache repeated searches where safe.
- Add request timeouts and rate limits.
- Avoid regenerating explanations unnecessarily.
- Monitor token usage, latency, and failures.

Do not assume that the LLM's own rating of relevance is a calibrated probability.

A numerical relevance score can be used for sorting, but the initial interface does not need to expose it to users.

## 17. Security and Reliability

- Keep all secret API keys on the server.
- Validate and limit search query length.
- Validate filter values.
- Rate-limit expensive requests.
- Handle TMDB and LLM outages gracefully.
- Validate model output against a schema.
- Match ranked IDs to the original retrieved candidate set.
- Escape untrusted content when rendering.
- Do not let user input override system instructions.
- Do not treat LLM-generated factual statements as verified metadata.
- Follow TMDB attribution, branding, and API usage requirements.
- Review the applicable LLM provider's data and privacy policies.

Since there are no user accounts, do not collect unnecessary personal information.

Verify that:

- TMDB results are retrieved.
- Duplicate movies are removed.
- Results are ranked.
- AI explanations appear on cards.

- Empty results are handled correctly.

### AI quality testing

Create a test set of representative queries.

Evaluate:

- Whether top-ranked results match the intent.
- Whether explicit constraints are respected.
- Whether explanations reflect real movie metadata.
- Whether rankings remain reasonable for vague queries.
- Whether different but relevant alternatives appear.
- Whether unsupported claims or invented movies are prevented.

Compare the system against a simple baseline, such as TMDB results sorted by rating.

### Performance testing

Measure:

- End-to-end search latency.
- TMDB request latency.
- LLM request latency.
- Average cost per search.
- Error rate.
- Cache hit rate, if caching is implemented.

## 24. Final Product Definition

The MVP is a responsive web application where users describe the kind of movie they want to watch in natural language, optionally apply structured filters, and receive up to 20 movies ranked by an LLM using candidate data retrieved from TMDB.

Each result includes movie metadata and a concise, query-specific explanation. Users can save movies to a browser-local watchlist without registering.

The core differentiator is not simply searching a movie database. It is translating subjective interests into relevant movie candidates and explaining why those movies fit.

The initial implementation should prioritize reliable candidate retrieval, grounded AI ranking, clear explanations, low operational complexity, and a working end-to-end user experience.
